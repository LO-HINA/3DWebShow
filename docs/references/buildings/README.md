# LOHINA 建筑风格参考与下一轮改造简报

更新：2026-10-23。本文件保留参考整理阶段的观察和建议；该阶段没有修改建筑或导入外部资产。之后用户已授权实施，八栋建筑已接入实体窗与统一光影，并完成第二轮立面构造细化，详见 [当前实施与验收记录](../../city-style-review/README.md)。当前仍缺本轮运行截图、连续录屏与真实 GPU 性能验收；下文“建议”“下一轮”描述不等于全部未实施。总规范仍以根目录 AGENTS.md 与用户最新指示为准。

## 1. 本轮提炼的方向

**深色媒体建筑街区：以有体量的建筑组织巨幅画面、竖向字牌和街边灯箱，再以局部辉光及湿地面倒影连接空间。**

这是一份根据用户已选参考推导的实施简报，具体楼型、媒体内容与亮度尚待样板确认。青、紫、品红、琥珀和少量红色可以按建筑分配主次，避免全城只套同一种灯带和招牌。深色墙体保留轮廓、转折和入口，不把通路和可交互门口一并压黑。

## 3. 三个项目的用途与接入边界

### Threejs-Punk / threejs-conference

建议研究霓虹画面、湿地面及有限分辨率的反射如何共同形成氛围。其 [地面源码](https://github.com/ektogamat/threejs-conference/blob/main/src/world/ground/createGround.js) 使用 TSL 节点材质和单独的镜面相机渲染，并提供反射尺寸、跳帧控制。对 LOHINA 的启发是把反射作为独立可调成本，与材质湿润程度共同处理。

[仓库说明](https://github.com/ektogamat/threejs-conference#license-and-assets)区分了 MIT 代码与 public 内的外部素材；复制具体代码前保留版权及相关署名，模型、图片、视频、音频逐项检查来源。当前没有复制其源码。

### Neon Zenith

建议研究立面开间、层高、窗间墙、房间视差、近景构件和实例化的分工。[建筑源码](https://github.com/billpwchan/neon-zenith/blob/main/src/city/buildings.js)将楼体分段、风格和立面属性分开处理；对 LOHINA 可先落实为少量可读建筑的参数化立面，不照搬城市规模。

其[许可证](https://github.com/billpwchan/neon-zenith/blob/main/LICENSE)为 MIT；[CREDITS](https://github.com/billpwchan/neon-zenith/blob/main/CREDITS.md)另列模型、纹理和字体的许可与来源。若选用某件资产，应按对应条目核验和署名，不能把代码许可扩展为所有资源的许可。

### Samsy 重建研究

建议结合用户截图研究媒体面的尺度对比、建筑暗面、竖向排版和地面反射的构图关系。[仓库 README](https://github.com/boyang-hu/samsyninja-rebuild)说明其为逆向重建、镜像资源归原站作者，供个人学习研究。本轮只阅读研究资料，不导入 mirror、原站模型、广告、字体、音乐或逐行复刻代码；未来需要具体复用时单独确认授权。

## 4. 建筑改造要同时解决的五层关系

1. **剪影和体量**：主楼有明确的主体、退台或出挑、冠顶与入口基座；增加楼体侧面与背面的可读性。塔楼和低层馆保持不同轮廓。
2. **媒体立面**：先决定主要观看面、主画面的比例与位置，再布置窗格、竖梃和结构框。主屏、竖向字牌、街边小灯箱有明显尺度差。
3. **实体支撑和进深**：屏幕有内凹位或结构框，侧挂招牌有支架和厚度，窗户有窗框与窗台，屋顶有女儿墙或设备。避免浮贴平面。
4. **行人尺度**：入口、雨棚、底层窗、卷帘和少量设备集中在近地层。空调、管线、售卖机等按位置补充，避免平均撒满每栋楼。
5. **光影反馈**：局部暖入口与冷屏幕分区；辉光服务于少数重点发光面；湿地面保留干湿差、粗糙度和反射衰减。低画质关闭增强后仍须辨认门口与建筑轮廓。

建议先制作三种互补角色，而非批量同款高楼：

| 建筑角色 | 外观重点 | 留白 |
| --- | --- | --- |
| 主视觉媒体塔 | 一幅有尺度的主画面、竖向辅助牌、明确冠顶 | 主屏周围的暗色结构面 |
| 商业街楼 | 错落侧挂牌、店面、雨棚、窗格和局部设备 | 分组招牌之间的楼体暗面 |
| E-01 展馆 | 清楚入口、橱窗与作品窗，保持低矮身份 | 入口侧墙和安静墙面，避免全馆铺广告 |

这些是建筑角色建议，尚未指定新 entityId、布局位置或更改各实体负责人。

## 5. WebGPU / TSL 是可评估的技术选项

用户已询问迁移可行性，不能继续把“现有 WebGL 工程”写成永久禁止 WebGPU/TSL 的理由。[官方 WebGPURenderer](https://threejs.org/docs/pages/WebGPURenderer.html)支持 WebGPU 和 WebGL2 后端；具体功能仍需分别验证。

当前工程中的媒体塔流光、地面渐隐使用 GLSL ShaderMaterial；该材质按[官方说明](https://threejs.org/docs/pages/ShaderMaterial.html)仅支持 WebGLRenderer，迁移时需重写。角色控制、布局数据与多数几何可继续沿用。建议独立验证一个建筑、屏幕与反射地面后，再决定渲染器迁移范围；本轮未实施迁移，未承诺帧率提升。

建筑模块和渲染增强分开交付：建筑负责人负责几何、立面和媒体槽；整合负责人统一处理渲染器、地面、后期、共享材质与碰撞，不在多个建筑模块中重复建立反射相机或渲染循环。

## 6. 建议的第一轮实施范围与验收

先选一栋由整合负责人明确分配的主视觉建筑做样板，检查当前已有 `heroBuilding.ts`、`mediaTower.ts` 及未提交成果，避免同一实体出现两个最终版本。复用已有图片/视频通道和大屏打开关闭行为；现有照片不能被新演示图静默覆盖。

先提交灰模体量和媒体面布局，再确认材质与光影。首轮不扩整张地图、不替换移动控制器、不同时开启雨、景深、CRT、强色差等所有效果。

交付应包含：

- 相同出生、正常行走、侧前方和近景入口机位的前后对比，分别说明体量、媒体面和入口变化。
- 街道两侧观看，以及转身/仰视后的侧面与背面，避免只做一个正面。
- 增强效果开关对比；真实设备、分辨率、画质、draw calls 与帧耗记录。未测量就标未测量。
- 独立模块、材质/媒体槽接口、碰撞变更建议和资源回收说明。布局、碰撞、共享场景由整合负责人统一接入。

**可直接发给建筑 agent 的任务摘要：**

> 先阅读本目录三张截图、README、docs/STYLE_REFERENCES.md 及当前建筑源码。把已分配建筑改成深色媒体建筑：用完整体量、巨幅主画面、竖向排版和近地店面形成层次。屏幕有实体结构，入口保持可读；媒体内容沿用 LOHINA 自有资源。先交体量与媒体布局同机位对比，选定后再细化。只修改分配给你的独立建筑模块，提出布局/碰撞/渲染需求供整合负责人处理。WebGPU/TSL 可提出单独验证方案，本轮不自动授权迁移或导入第三方资产。
